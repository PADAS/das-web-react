# ERA-12930 — Feed table view

The Events and Patrols feeds expand into a full-width, sortable table of the same list. The table is not a separate place: it uses the feed's filters and sort, and collapses back to the cards. Subjects (Q4) gets the same treatment.

This replaces the earlier dedicated Data tab, which duplicated the feeds and their filters.

## Behavior

- **Expand / collapse:** a button in the feed header. The panel widens across the screen and the table fades in. The state is in the URL (`?view=table`), so Back undoes it and shared links keep it.
- **Remembered choice:** events and patrols each remember feed or table in this browser. A list URL without `?view` (a reload, the tab, the way back from an item) opens the remembered view, adding `?view=table` in place rather than as a new history entry. A URL with `?view` wins and becomes the remembered choice. Back and Forward show a history entry as it was, so Back still undoes an expand.
- **Filters:** the feed's own filters, above the table. No separate column filters.
- **Sorting:**
  - Events: event time, updated, created and serial number columns sort through the events API (`sort_by`), the same sort the feed uses. Other columns don't sort, since the API can't order by them and sorting only loaded pages would be wrong.
  - Patrols: the API has no ordering, so the table loads every page and sorts client-side on any column.
- **Opening a row:** opens the existing event or patrol details in place of the table and moves the map to the item. Going back to the list, by Back, the tab or the header, brings the table back. No in-table drill-down.
- **Event type columns:** filtered to a single event type, each field in that type's schema gets a column (titled from the schema), even when no loaded event has a value for it. The feed loads event details for the values. Plain values, choices (by their label), dates and numbers show in the cell. Object and list fields (the schema type decides) show a link that opens a read-only view of their keys and values, nested ones opening in place. Without a schema, the columns come from the loaded event details.
- **Table-only tools:** multi-select (cleared on collapse), bulk resolve / reopen / add to patrol / add to incident for events (through the event menu's patrol and incident pickers, one request per event; events already on a patrol or in an incident, and incidents themselves, are skipped and counted as not updated), CSV export of events through the events export API, the same file as the menu's Field Events export (patrols have no export yet), and a column picker. Each table remembers in this browser which columns are hidden, the order they were dragged into and their widths. Filtered to one event type, the order including that type's field columns is remembered for that type on its own; the table's other columns keep their order across types, and columns it hasn't seen before go at the end.
- **Narrow screens:** the same toggle; the panel is already full-width there.

## Code

- `src/FeedTable/` — `FeedTable` (shared grid host: toolbar, columns, selection, export), `EventsTable`, `PatrolsTable`, `useFeedTableView`.
- Feeds render the table in place of their list: `SideBar/EventsManager/EventsFeed`, `SideBar/PatrolsManager/PatrolsFeed`, legacy `SideBar/PatrolsFeed`.
- `SideBar/useReportsFeed` asks for event details when the table is filtered to one type. Map and realtime fetches skip details but answer `event_details: null`; the event store keeps details already loaded rather than taking that null.
- `FeedTable/eventTypeFields.js` reads the columns from v1 and v2 schemas; `FeedTable/ObjectViewModal` is the object view.
- AG Grid Community only (`ag-grid-community`, `ag-grid-react`).
